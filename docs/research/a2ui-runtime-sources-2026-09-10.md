# A2UI runtime composition: source review

Research date: 2026-09-10. Scope: the four articles below, read in full, with their technical claims checked against official specifications, documentation, package metadata, and source. This is research, not an implementation change or a reproduced performance benchmark. Product implications are identified as recommendations rather than claims about existing SpecSync behavior.

## What the four articles establish

### Runtime UI, May 1, 2026

[A2UI in Angular: How AI Generates Dynamic UIs at Runtime](https://www.angulararchitects.io/en/blog/a2ui-how-ai-generates-dynamic-uis-at-runtime/) demonstrates a catalog-controlled interface using the then-draft v0.9 protocol. Its example first creates a surface and an ID-linked component tree, then supplies passenger data separately. Property bindings refer to data paths. A button declares an event with bound context; the Angular handler updates the local model. This demonstrates both runtime composition and a small interaction loop, although the example constructs the messages in application code rather than asking a model to generate them.

The renderer uses Angular signals and an imperative processing API. Its event subscription requires explicit lifecycle cleanup. The useful architectural distinction is that the server describes an interface while registered client components determine its implementation and appearance. The article's statement that v0.8 was stable and v0.9 draft is historical, not today's release status.

### AG-UI integration, May 1, 2026

[Integrating A2UI with AG-UI and CopilotKit in Angular](https://www.angulararchitects.io/en/blog/integrating-a2ui-with-ag-ui-in-angular/) carries operations in an `ACTIVITY_SNAPSHOT` with `activityType: "a2ui-surface"`. It explicitly presents this as an integration convention and mentions ordinary server tool results as an alternative. The model produces tool arguments; validation errors can return to it before successful operations reach the client.

The displayed activity schema checks an operations array but uses `z.custom<A2uiMessage>()` for entries; this is not full operation validation. Its renderer handles each surface ID once, so copying that guard would skip subsequent snapshots for an evolving surface. Its lifecycle cleanup and one-build-per-ID assumption must be reconsidered for persistent workspaces. Helpers such as `initAgentStore`, `sendMessage`, and `useServerMemory` belong to the example project rather than constituting a portable CopilotKit API contract.

### Custom catalogs, May 1, 2026

[Custom Catalogs in A2UI: Your Own Components for AI-Generated UIs](https://www.angulararchitects.io/en/blog/custom-catalogs-in-a2ui-your-own-components-for-ai-generated-uis/) registers ordinary Angular components with property schemas and signal-based context. Its passenger progress widget illustrates how domain components can expose useful semantic inputs instead of inviting the model to reconstruct low-level markup. Registered functions offer another controlled extension point.

The example's `extraComponents` augments BasicCatalog, whereas its `functions` option replaces the defaults and therefore explicitly includes the basic functions. Its helper factories and catalog-context plumbing are application utilities. The article recommends sending only a catalog identifier in production and resolving trusted descriptions server-side; its development example can instead transmit schemas through agent context. Catalog identity must agree with the surface declaration. An identifier that resembles a URL does not imply arbitrary remote component loading.

### DSL and performance, May 29, 2026

[A2UI with a DSL: Controllable Dashboards Optimized for Performance](https://www.angulararchitects.io/en/blog/how-i-made-my-a2ui-dashboard-300-times-faster/) moves the model's work from writing complete A2UI and arranging data calls to selecting dashboard tile types and options. Application code retrieves data and compiles the description into A2UI. The client still receives the same protocol.

The reported baseline is roughly 40 seconds and over 46,000 tokens. The compact DSL reduces the reported token count to roughly 1,500; an uncached DSL run still takes a few seconds. The approximately 0.1-second result uses a cached DSL and no model call. Thus the headline's 300× improvement combines DSL simplification and cache reuse; it does not measure a fresh model call or an Angular renderer acceleration. Rounded timing values cannot establish an exact ratio. The article supplies no controlled benchmark methodology, distributions, or environment sufficient to predict SpecSync's improvement.

## Current status and source drift

The [official A2UI site](https://a2ui.org/) now identifies **v0.9.1 as the production version**, v0.9 as previous stable, v0.8 as legacy, and v1.0 as a candidate. The May articles' release labels should not be copied into current architecture decisions. Protocol versions and npm package versions are different numbering systems.

Package metadata checked on the research date reports [`@a2ui/angular` 0.10.6](https://registry.npmjs.org/@a2ui%2fangular/0.10.6) with Angular peers `^21.2.5`, while [`@copilotkit/angular` 0.5.2](https://registry.npmjs.org/@copilotkit%2fangular/0.5.2) declares Angular `^22.0.0`. For SpecSync's Angular 22 application, directly adopting the former requires a compatibility decision and verification; a peer mismatch alone does not prove runtime failure. No compatibility experiment was performed in this research.

Current A2UI source differs from the tutorial: [`BasicCatalogBase`](https://github.com/a2ui-project/a2ui/blob/ec20cff14a021aff96f735f5bf8177ab6ee8d6a8/renderers/angular/src/v0_9/catalog/basic/basic-catalog.ts) marks `extraComponents` and `functions` deprecated in favor of constructing `AngularCatalog` with explicit component/function collections. It also uses a different default basic-catalog identifier. A dedicated [`CatalogComponentInstance`](https://github.com/a2ui-project/a2ui/blob/ec20cff14a021aff96f735f5bf8177ab6ee8d6a8/renderers/angular/src/v0_9/core/catalog_component_instance.ts) interface now exists. The [renderer service](https://github.com/a2ui-project/a2ui/blob/ec20cff14a021aff96f735f5bf8177ab6ee8d6a8/renderers/angular/src/v0_9/core/a2ui-renderer.service.ts) exposes `provideA2Ui`, accepts catalogs and an optional action handler, and disposes its model on destruction. These are source observations at a pinned revision, not an assertion that all examples work unchanged with every published package.

The example repository also changed: its current [activity renderer](https://github.com/angular-architects/flights42/blob/7c87295c69d8cd9f2140993c05f3af027065e43c/src/app/domains/shared/util-copilotkit/a2ui/a2ui-activity-renderer.ts) processes operations on each effect invocation and labels the integration legacy. It is not identical to the article's deduplication/cleanup snippet. The branch snapshot is evidence of the present implementation, not a recovered publication-time revision.

## Protocol and integration facts that matter

The [v0.9.1 specification](https://a2ui.org/specification/v0.9.1-a2ui/) defines surface creation, component updates, data updates, and deletion. Create a surface before updating it; its catalog and identity do not change through another create. Component references form a flat ID graph rooted at `root`. `updateDataModel` replaces the value at its selected path: it is not an implicit recursive merge. A missing path or `/` targets the entire model. Catalog IDs are identifiers and need not be downloadable URLs. Interactive transports need ordered delivery and a return path for actions; the specification does not mandate this tutorial's particular activity envelope.

The official [actions guide](https://a2ui.org/concepts/actions/) separates local registered function calls from events returned to an agent. Bound event context is resolved to values; inputs can update local model state without a network round trip per keystroke. In v0.9, the client action includes its name, surface, source component, timestamp, and context. Client validation improves feedback but does not replace server validation. Enabling `sendDataModel` transmits the surface model in metadata, so it requires deliberate scoping. These details make ownership and routing of an existing surface part of the application contract, beyond displaying a first snapshot.

The official [catalog guide](https://a2ui.org/guides/defining-your-own-catalog/) supports defining schemas around the application's design system, registering their implementations, and announcing supported catalog IDs. It recommends trusted component allowlists, property validation, and text sanitization. A useful SpecSync interpretation is to expose vehicle comparison, evidence, and clarification semantics through approved components; a schema remains separate from permission to access data or execute an action.

Under [AG-UI event semantics](https://docs.ag-ui.com/concepts/events), an activity snapshot replaces activity content by default, while an activity delta applies ordered JSON Patch operations. Activity messages are client-side by default and stripped from `RunAgentInput`; their presence does not establish durable backend history. Tool results correlate with tool calls, and tool-call end signals the end of arguments rather than necessarily completed execution. Therefore transport selection must account for replay, persistence, and update ordering, not only visual rendering.

Current official [`CopilotActivity`](https://docs.copilotkit.ai/reference/angular/components/CopilotActivity) supports registered Angular activity renderers and schema validation, including presentation outside the chat. The current [Angular generative UI guide](https://docs.copilotkit.ai/angular/guides/frontend-tools-generative-ui) also distinguishes rendering known tool results from A2UI's dynamic operation-based rendering. The [Mastra runtime documentation](https://docs.copilotkit.ai/angular/mastra/copilot-runtime) describes enabling A2UI middleware. These document available integration paths; they do not establish that the exact APIs are present in SpecSync's installed dependency versions.

[Angular's programmatic rendering guide](https://angular.dev/guide/components/programmatic-rendering) provides native mechanisms for selecting compiled component types and binding their inputs at runtime. Dynamic composition need not mean compiling model-written templates. The [effects guide](https://angular.dev/guide/signals/effect) supports effects for imperative renderer integration and cleanup while favoring computed signals for derived values. Surface processing should consequently avoid accidental repeated creation, preserve stable component identity where appropriate, and explicitly clean up subscriptions.

## What the DSL implementation actually does

The pinned example [`renderDashboard` tool](https://github.com/angular-architects/flights42/blob/7c87295c69d8cd9f2140993c05f3af027065e43c/ai-server/src/mastra/tools/render-dashboard.ts) accepts the dashboard schema and returns a small acknowledgement. The [AG-UI route](https://github.com/angular-architects/flights42/blob/7c87295c69d8cd9f2140993c05f3af027065e43c/ai-server/src/mastra/routes/dashboard-ag-ui-route.ts) intercepts those arguments, invokes compilation, and emits an A2UI activity. On a cache hit it bypasses the model but still compiles the dashboard and emits run/tool/activity events. This explains why a warm result is qualitatively different from an uncached model execution.

The [compiler](https://github.com/angular-architects/flights42/blob/7c87295c69d8cd9f2140993c05f3af027065e43c/ai-server/src/mastra/dashboard-dsl/compile-dashboard.ts) gathers data, deduplicates flight routes, performs parallel requests, and assembles components and model updates. It accepts an injected surface ID but generates a UUID otherwise. Some structure depends on fetched row counts. Consequently, deterministic compilation means application-controlled construction for specified inputs and data, not byte-identical output across refreshed data and newly generated IDs.

The [DSL schema](https://github.com/angular-architects/flights42/blob/7c87295c69d8cd9f2140993c05f3af027065e43c/ai-server/src/mastra/dashboard-dsl/dashboard-spec.ts) is a useful example vocabulary rather than a production resource policy: its tile array has a minimum but no maximum, and several positive row-limit options lack upper bounds. SpecSync should retain explicit panel, row, attribute, payload, and request budgets rather than copying these bounds unchanged.

The [cache](https://github.com/angular-architects/flights42/blob/7c87295c69d8cd9f2140993c05f3af027065e43c/ai-server/src/mastra/cache/dashboard-cache.ts) stores parsed DSL in local files, keyed by a hash of concatenated user-message text. The implementation shown does not incorporate a tenant, catalog/compiler version, or expiry into that key. It validates cached descriptions on read. This is not a ready-made cache policy for a stateless, multi-user service. If SpecSync later caches plans, scope and invalidation need their own design; factual evidence still needs an explicit freshness policy.

## Implications for SpecSync — recommendations

| Runtime use case               | Why the pattern fits                                                                                               | Contract needed beyond a first snapshot                                                                                      |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------- |
| Adaptive vehicle comparison    | Domain components can present retrieved values, uncertainty, and provenance while the DSL chooses relevant panels. | Clarify ambiguous trim/market/year, bind selected IDs, refresh the same surface, and preserve the user's current selections. |
| Evidence investigation         | The surface can expand from a comparison to specifications and reviews as the question changes.                    | Server-owned retrieval, bounded attributes/fanout, per-panel failure and retry, and sources preserved through updates.       |
| Research progress              | Runtime status can reveal which evidence is available or missing as work proceeds.                                 | Typed events, cancellation, ordered updates, and explicit history/replay behavior.                                           |
| Preference and filter controls | Local binding can provide immediate feedback before submitting a meaningful action.                                | Allowlisted actions and independently validated server inputs; avoid sending a full surface model unnecessarily.             |

These are design inferences from the sources, not claims that the current renderer implements these loops. A fixed column of bounded domain panels is a useful initial composition capability. Adaptive agentic interaction additionally requires typed client feedback, ownership of an existing surface, targeted updates, and stable UI state. The articles support building that incrementally around a compact DSL and a trusted catalog; they do not establish that unrestricted model-authored UI or a particular transport automatically supplies it.

The most useful first experiment is an evidence-backed comparison that asks a focused clarification when a vehicle identity is ambiguous, then updates the same workspace. Measure initial rendering and later updates separately, including model time, retrieval time, payload size, invalid-description retries, cancellation, and interaction-state preservation. Benchmark uncached and cached execution separately. No live SpecSync runtime, compatibility, or performance benchmark was performed for this source review.

# Mastra evaluation research for SpecSync

Research date: 2026-09-08. Scope: all eleven pages in the current Evals guide navigation, all evaluation and dataset reference pages listed in the official [documentation index](https://mastra.ai/llms.txt), and the tracing, metrics, and storage-exporter guides. This is a primary-source research note; the SpecSync contracts and thresholds below are proposals, not Mastra guarantees or measured production quality.

## Compatibility with this worktree

The lockfile pins `@mastra/core` 1.64.0, `@mastra/pg` and `@mastra/libsql` 1.22.3, and Vitest 4.1.11. At research start, neither `@mastra/evals` nor `@mastra/observability` was a dependency. The Mastra registry has storage and logging but no configured scorers or observability exporter. The app uses Zod 3.25.x, OpenRouter for model calls except Vertex search grounding, and existing Cloud SQL storage in the `mastra` schema.

The published **exact 1.64.0 npm package declarations** were inspected independently of the moving website: `dist/evals/base.d.ts`, `dist/evals/run/index.d.ts`, and `dist/datasets/*`. Core already exports `createScorer`, `MastraScorer.run`, `runEvals`, gates, thresholds, per-turn assertions, and workflow step/trajectory configuration. The initial deterministic benchmark therefore needs no additional evaluation package. A scorer can use functions throughout, without constructing a judge. `runEvals` targets agents or workflows; arbitrary functions belong in a workflow adapter or a runner that invokes `scorer.run` itself. [Core package metadata](https://registry.npmjs.org/@mastra%2fcore/1.64.0), [createScorer reference](https://mastra.ai/reference/evals/create-scorer)

Use the existing Zod line at the benchmark boundary. The core scorer's explicit custom `type: {input, output}` declaration refers to Zod v4 internally; an initial function scorer can omit that option and parse inputs using the app's Zod 3 schemas. Do not upgrade the shared Zod dependency to copy a documentation example.

Prefer explicit isolated evaluation resources and verify the exact execution path locally. A shared user chat thread must never be used to compare independent candidates.

## Proposed SpecSync evaluation contract

Evaluate three separate outputs: (1) user intent and vehicle identity resolution, (2) the complete document-family extraction into evidence-backed catalog candidates, and (3) the answer shown to the user. A correct answer for one requested trim does not prove successful catalog enrichment across a brochure.

Each gold case should carry its market, requested identity/ambiguity, immutable source snapshots and content hashes, expected model-year/configuration identities, atomic expected claims, applicable attribute denominators, permissible abstentions/conflicts, and accepted evidence locators. Each atomic claim binds a variant, field, raw value, unit, qualifiers (fuel, standard, conditions), availability state, and evidence revision/location. Confidence is nullable; absence means unknown, not zero confidence.

Scoring should use set matching with one-to-one matches, not textual similarity or a count of output rows. Duplicate output cannot increase recall. Wrong trim/year/market, shifted PDF columns, missing fuel qualifiers, or an optional feature presented as standard must be wrong even when the number and quote appear somewhere in the document. Citation existence and citation entailment are different checks.

| Metric                              | Proposed measurement                                                                                                                                                                                               |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Identity accuracy                   | Correct market/model-year/configuration key; ambiguity is resolved only with supported evidence or explicit user clarification.                                                                                    |
| Claim precision                     | Unique correctly supported predicted claims / all unique predicted claims. Unsupported extras reduce precision.                                                                                                    |
| Claim recall                        | Correctly supported expected claims / eligible gold claims. Empty output cannot pass through precision alone.                                                                                                      |
| Variant recall                      | Correct configurations extracted / configurations documented in the source family, beyond the requested trim.                                                                                                      |
| Evidence validity                   | Snapshot revision, page/line/table-cell locator, applicable headers, quote, and claim binding all agree.                                                                                                           |
| Qualifier and availability accuracy | Fuel-specific values, testing standards, standard/optional/unavailable/unknown, conditions, and units preserved.                                                                                                   |
| Abstention/conflict handling        | Missing facts stay unknown; disagreement remains represented until resolved; no speculative merge.                                                                                                                 |
| Confidence calibration              | Brier score and reliability bins on adjudicated supported/unsupported claims, plus precision versus coverage at chosen publication thresholds. Report missing confidence coverage separately.                      |
| Efficiency                          | Per-case wall time and time to first useful evidence; token/model/tool counts, fetched bytes, cost, retries and cache status.                                                                                      |
| Shared-search correctness           | Controlled concurrent same-key requests execute one claimed job; independent users receive authorized public progress/results; private context never leaks; disconnect/retry/restart preserve ownership semantics. |

Hard gates for a small **synthetic contract suite** should require every expected result and evidence binding, no duplicate/unsupported claims, and no runtime or schema failures. These are correctness fixtures, not estimated accuracy on real Brazilian vehicles. Real-corpus quality thresholds must be selected after labeling and baseline measurement; do not label a judge score as a calibrated reliability probability.

## Dataset growth and experiment design

Start with explicitly fabricated fixtures for the executable contract, then add licensed/public manufacturer pages and PDFs with human-adjudicated gold labels. Include cars, pickups, SUVs, motorcycles, light/heavy commercial vehicles and buses; older model years; scanned PDFs; multi-column tables; engine/fuel variants; packages; contradictions; partial/unavailable documents; and ambiguous queries such as the user's Ranger example. Representative seeds do not establish all-vehicle/all-year coverage.

Split by document family and generation/model-year cluster, so sibling pages or trims from the same brochure cannot leak between development, validation and held-out test. Keep immutable snapshots and semantic gold-schema/scorer versions in Git or existing approved artifact storage. Gold is withheld from the candidate and judges receive only the labeled evidence needed for their criterion. Candidate-generated labels require human review before promotion into gold.

Compare deterministic extraction, LLM extraction, and deterministic extraction with targeted LLM fallback on identical snapshots and budgets. Freeze discovery when testing extraction. Run discovery separately against fixed search/crawl recordings and a live freshness lane. Vary one prompt/model role at a time before comparing complete bundles. Record exact role model IDs, effort, prompts, SDK/package/commit versions, retrieval settings, judge version, source digests, retries, and warm/cold cache policy.

Use at least several independent repetitions for live model comparisons, report per-stratum precision/recall and worst-case failures, and bootstrap intervals grouped by document family. Record failed attempts rather than silently retrying until a pass. Choose among candidates that meet quality constraints by cost and latency; do not hide correctness losses in a weighted composite.

## Traces, cost and CI

Mastra traces can capture nested agents, tools and workflows, while its metrics cover execution duration, token usage and related operational signals. A storage exporter makes historical traces available in Studio; request context and payloads need deliberate selection. The initial benchmark should retain its own JSON report even before production observability is configured. [Tracing](https://mastra.ai/docs/observability/tracing/overview), [Metrics](https://mastra.ai/docs/observability/metrics/overview), [Storage exporter](https://mastra.ai/docs/observability/integrations/exporters/mastra-storage)

Instrument fetched source bytes, actual network attempts, extraction phase durations, provider-reported token usage/cost, and per-job subscribers separately from the framework's final answer score. Charge model usage once per research job, and distinguish research cost, judge cost, and user billing. Missing provider cost is `null`; zero means measured zero. Cache-hit latency should not be mixed with cold discovery.

Proposed lanes: deterministic offline contract checks on every relevant PR; pinned snapshot extraction runs on demand with an explicit model/budget; broader scheduled live discovery and quality samples after baseline costs are known; production sampled judges calibrated against human review. Deterministic concurrency/recovery tests should be a separate integration suite with real database constraints and controlled network stubs. A fixture simulating shared searches does not establish production deduplication.

The executable first slice is documented in `apps/ai/benchmarks/README.md`. It intentionally uses core scorers with a standalone runner; stored Mastra datasets/experiments can later ingest the same versioned results using caller-driven APIs without changing the scoring contract.

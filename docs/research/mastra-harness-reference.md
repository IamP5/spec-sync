# Mastra harness reference for SpecSync

Research date: **2026-09-08**. This is a source-backed design reference, not an implemented harness or a production-readiness claim. The companion SpecSync design owns the proposed catalog and evaluation contracts.

## Scope and compatibility

All **eight pages in the Harness navigation** were read, including their complete Markdown versions. Discovery used the [official documentation index](https://mastra.ai/llms.txt) and the [Harness overview](https://mastra.ai/docs/harness/overview); the index omits some overview links, so the sidebar was checked too. Relevant linked references and adjacent workflow, storage, memory, guardrail, and subagent documentation were also consulted below. This does not claim every page across the entire Mastra website was reviewed.

The worktree currently installs and locks `@mastra/core` **1.64.0**, `@mastra/memory` **1.28.2**, `@mastra/pg` **1.22.3**, and `mastra` **1.27.3**. Local embedded documentation and declarations were checked alongside the current website. Several harness APIs are explicitly beta, allowing breaking changes without a major version increment. Do not upgrade or copy current snippets without checking the installed declarations.

Repository constraints came from [the AI agent guide](../../apps/ai/AGENTS.md): verified identity, private per-user chat memory, Cloud SQL, stateless Cloud Run instances, Mastra's existing HTTP surface, role-based OpenRouter routing with the specific Vertex grounding exception, and API-owned wallet/catalog state. The [cross-app routing contract](../openrouter-model-routing.md) and `apps/ai/src/mastra/models.ts` define model roles, separate user and operating budgets, and OpenRouter reasoning options. No new persistent store or infrastructure was added by this research.

## Execution, recovery, and subscriptions

[DurableAgent's reference](https://mastra.ai/reference/agents/durable-agent) exposes `stream`, `prepare`, `resume`, `observe`, `recover`, `listActiveRuns`, and `recoverActiveRuns`. An observer can resume from an event offset; optional idle timeout and liveness checks prevent waiting forever after producer death. **Its `cleanup()` destroys run registry entries and retained events. It is not a harmless per-browser unsubscribe.** Suspended runs must retain the state needed for resume. `abortRunStream(runId)` publishes cancellation through the shared transport; the documented effective cancellation behavior requires core 1.62.0+. `abortThreadStream` needs a locally known thread runtime. A caller-supplied run ID identifies execution but does not prove that concurrent identical starts are coalesced.

SpecSync should expose its own authenticated research subscription and detach operation. Detaching one user must not cancel a shared worker or clean up other users' replay state. The application should retain a catalog result and event sequence independently of the agent's automatic cleanup window. Define explicit semantics for final-subscriber cancellation and catalog enrichment continuation.

### Installed 1.64.0 resolves a documentation contradiction

The durable guide says both that automatic recovery holds a lease and that replicas have no distributed recovery lock. The second statement is not universally true of this installed release. Source embedded in `node_modules/@mastra/core/dist/create-durable-agent-76UE00WE.js.map`, `src/agent/durable/durable-agent.ts`, implements a separate recovery lease:

- It extracts a real `LeaseProvider` from the transport, including through `CachingPubSub`, or falls back to `NoopLeaseProvider`.
- Its key contains the agent ID and run ID; each recovery attempt has a new random owner. This distinguishes two recoverers of the same logical run.
- It checks ownership during recovery, renews the lease, and handles loss. A local claims map additionally prevents duplicate recovery within the process.

This is observed installed-code behavior, not a distributed fault-injection result. It does not make database commits, external fetches, model billing, or arbitrary side effects exactly once. A transport with no real leasing still cannot coordinate recoverers across replicas. Test the pinned backend under process death, delayed renewal, and concurrent recovery before enabling automatic recovery.

Installed declarations also identify an important serialization boundary: closure-only `stopWhen`, per-call `prepareStep`, completion scorer instances, and delegation callbacks cannot simply be reconstructed from a workflow snapshot. The [durable reference](https://mastra.ai/reference/agents/durable-agent) documents degraded behavior across processes. SpecSync's financial admission and catalog acceptance rules therefore need durable enforcement in the API/worker protocol, not a request closure. The existing `stopWhen` charging contract needs explicit migration tests before wrapping the chat agent durably.

## Proposed SpecSync interpretation

These are application requirements inferred from the user's goals and the runtime boundaries above, rather than promises made by Mastra:

1. **Share public research work, not user conversations.** The target market is Brazil across all vehicle categories and years. Resolve vehicle type/make/model family/market/model year before matching a job. Ambiguous requests need an unresolved-intent state. A model-family research key can serve several trim requests; keep user-specific filters and private uploads outside the shared key.
2. **Coalesce at multiple levels.** An active research claim prevents duplicate discovery; normalized URLs plus immutable content hashes identify document versions; extraction cache keys also include schema, parser, prompt, workflow, and model versions. Two URLs may contain the same brochure; one URL may later change contents.
3. **Extract the source's full supported configuration matrix.** First discover document scope, column/row structure, model years, markets, variants, and footnotes. Then extract claims for every supported configuration, prioritizing the requested variant for first useful results. Do not combine independent option choices into invented purchasable configurations.
4. **Use deterministic and LLM stages where each can be verified.** Fetch, hashing, MIME validation, text/table extraction, units, ranges, duplicates, and schema checks are deterministic. Identity resolution, difficult layout interpretation, multilingual labels, scanned pages, and footnote mapping are suitable model stages. Escalate only when extraction quality or unresolved conflicts justify the extra cost.
5. **Represent evidence at the claim level.** Keep immutable artifact ID/hash, original and resolved URLs, retrieval time, page/table/cell or text span, raw value/unit, normalized value/unit, applicability, method, and exact pipeline/model versions. One citation for the entire response is insufficient for a PDF covering multiple engines or markets.
6. **Separate observed facts, unknowns, conflicts, and inferences.** Confidence is not the model's self-reported certainty. Treat calibrated correctness, source quality, citation support, and catalog coverage as distinct measurements. Repeated copies of one brochure are not independent corroboration. Preserve contradictory claims for reconciliation.
7. **Bound work before each paid operation.** Include nested model calls, judges, OCR/vision, retries, resumed calls, and speculative catalog enrichment in the budget ledger. A completed requested answer and an ongoing broader catalog-enrichment job can have different priorities and budgets.
8. **Make publishing idempotent and progress replayable.** Enforce claim/event uniqueness and worker ownership in the authority that commits them. Replay events by stable sequence; accept retries without duplicate catalog writes. Persist final results beyond transient Mastra stream retention.

## Required compatibility experiments before choosing a runtime

These tests complement the accuracy evaluation process; they do not need live LLMs except for measured model-cost recovery experiments.

| Scenario                                                                | Acceptance evidence                                                                                                     |
| ----------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| Two users request the same family simultaneously on different instances | One authoritative active job; both receive authorized progress and their own filtered answer.                           |
| Different trim requests share one family brochure                       | One captured/extracted artifact version; distinct configuration-specific claims without column leakage.                 |
| One observer disconnects or cancels                                     | Other observers continue; no shared `cleanup()` or worker abort is triggered by detachment.                             |
| A late observer joins after completion and replay-cache eviction        | Final catalog result and durable progress snapshot remain available.                                                    |
| Worker dies after a fetch/model call/commit but before acknowledgment   | Recovery repeats only allowed work; no duplicate published facts or ledger effects; repeated provider usage is visible. |
| Two instances recover one run; lease renewal is delayed or lost         | One effective writer, stale ownership rejected, no unbounded duplicate model work.                                      |
| Recovery loses request closures                                         | Budget, identity, allowed tools, acceptance gates, and model-role selection remain correct.                             |
| Background task suspends, process restarts, then resumes                | Executor registration and persisted payload recover correctly; one terminal result is published.                        |
| PubSub or cache temporarily fails                                       | No silent claim loss; replay status is explicit; event delivery retry does not duplicate accepted results.              |
| A malicious document supplies instructions or misleading applicability  | Document content remains untrusted evidence; unsupported or wrong-market claims fail validation.                        |

The architecture decision should compare a deterministic workflow baseline, a workflow with targeted LLM recovery, and a bounded agent-driven alternative using the same fixtures, budgets, and acceptance contract. Choose from measured precision, coverage, latency, cost, and recovery behavior rather than from the number of harness features enabled.
